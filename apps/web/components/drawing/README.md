Актуально на 23.10.2026, гілка `feature/BIM-60`. Це локальний frontend-стенд

## Запуск і перевірки

Із кореня репозиторію у PowerShell:

~~~powershell
npm.cmd run build
npm.cmd run start
~~~

Відкрийте **http://localhost:3000/drawing-preview**. Кореневий маршрут `/`
наразі повертає порожню сторінку. Для розробки: `npm.cmd run dev`.

Файл відкривається у браузері через object URL і не надсилається на сервер.
Основні fixtures: `apps/api/tests/fixtures/test_drawing_dxf/`;
український синтетичний fixture: `apps/web/tests/fixtures/dxf/04_ukrainian_text.dxf`.

~~~powershell
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run test
npm.cmd run build
~~~

Усі чотири команди успішно виконані. Для BIM-60 відновлено відсутні вже
оголошені npm-пакети (зокрема `@supabase/ssr`); manifest і lockfile не змінено.
Тести contracts також проходять; змін/регенерації контрактів не потрібно. Node-тести геометрії
не замінюють браузерне або хостингове приймання.

## Межі компонентів і координати

- `drawing-viewer.tsx`: Client Component, `next/dynamic` із `ssr: false`,
  retry та оформлення через кореневий `tokens.json`.
- `drawing-canvas.tsx`: lifecycle адаптера, loading/ready/error, WebGL context
  loss, вимірювання часу й cleanup.
- `drawing-preview.tsx`: input, Drag & Drop, валідація та object URL.
- `lib/drawing/viewer-adapter.ts`: межа `dxf-viewer@1.0.50`, камера,
  fit/zoom/resize, WCS ↔ CSS pixels і viewport subscriptions.
- `lib/drawing/load-timings.ts`: інтервали за публічним progress API.

`DrawingViewer` приймає `url` (локальний object URL або вже отриманий signed
read URL), необов'язкові `fileName`, `onReady`, `rooms?: Room[]`, `devices?: Device[]`
і `initialRoomLabelsVisible` (типово `true`). Компонент не отримує
авторизований URL самостійно і не припускає конкретного поля відповіді API.

`onReady(controller)` надає контролер; `onReady(null)` завершує його
використання. `worldToScreen` / `screenToWorld` працюють у вихідних DXF WCS
без перетворення мм у метри. CSS pixels відлічуються від canvas;
scene = WCS − GetOrigin(). GetBounds() повертає WCS, FitView очікує scene.
Майбутні оверлеї мають використовувати цей контролер, а не незалежну камеру.

Зміна URL або Retry створюють нову сесію і renderer. Pan/zoom/resize не
запускають повторний Load. Відкладений скасовуваний старт прибирає зайвий
Load під час Strict Mode effect replay у dev. Dispose одразу прибирає
canvas, ResizeObserver і підписки; за наявності pending Load знищення WebGL
відкладене до його завершення. AbortSignal бібліотека не підтримує;
застарілі результати не змінюють поточний UI.

## Українські TEXT/MTEXT і шрифт

`fonts.ts` передає `fonts: [...DRAWING_FONT_URLS]` у кожний Load.
Використовується локальний незмінений Noto Sans Regular TTF 2.008:
`/fonts/noto-sans/NotoSans-Regular.ttf`. Джерело, checksum і SIL OFL —
у `public/fonts/noto-sans/README.md` та `OFL.txt`.

Шрифт читається ліниво, коли потрібен текст; байти може повернути HTTP-кеш,
але розібраний opentype font між сесіями бібліотека не кешує. Попри старий
коментар бібліотеки про typeface.js, встановлений loader читає TTF через
fetch/ArrayBuffer та opentype.parse. Це ресурс геометрії, не CSS @font-face.
Без fonts параметра текстова геометрія не будується.

Fixture `04_ukrainian_text.dxf` містить рамку 24 000 × 14 000 WCS і:

| Тип | Текст | Вставка X/Y | Висота | Поворот |
| --- | --- | --- | ---: | ---: |
| TEXT | Кімната 101 — Office | 1000 / 12000 | 500 | 0° |
| TEXT | Ґґ Єє Іі Її 0123456789 | 1000 / 11000 | 500 | 0° |
| MTEXT | Кухня / Kitchen; другий рядок Площа 24 м² | 1000 / 9000 | 500 | — |
| TEXT | Українська абетка великими літерами | 1000 / 5000 | 350 | 0° |
| TEXT | Українська абетка малими літерами | 1000 / 4000 | 350 | 0° |
| TEXT | Вихід / Exit | 22000 / 2000 | 500 | 90° |

MTEXT має ширину 18 000, attachmentPoint=1 і розрив рядка `\P`.
Апострофів у вихідному fixture немає.

## BIM-60: оверлей і демонстрація

У `/drawing-preview` натисніть **«Відкрити демо оверлею»**. Це явний локальний
режим із `01_simple_rooms_mm.dxf`: кімнати 0–4000 × 0–5000 (20 м²),
4000–9000 × 0–5000 (25 м²), 0–9000 × 5000–9000 (36 м²).
Позиції чотирьох пристроїв ілюстративні, не результат нормативного розрахунку.
Відкриття будь-якого локального файла, навіть із таким самим ім'ям, прибирає
демодані. Закриття/заміна відкликає object URL. Auth-proxy пропускає точний
шлях `/drawing-preview` лише при `NODE_ENV=development` (`npm.cmd run dev`),
тому локальний стенд не потребує Supabase-конфігурації. У production цей
маршрут викликає `updateSession()` і потребує звичайної конфігурації Supabase.

Лише кнопка демо використовує `DEMO_DISPLAY_DXF`: копію в пам'яті без трьох
TEXT-сутностей `Room_101 (20.0m2)`, `Room_102 (25.0m2)`, `Room_103 (36.0m2)`
на шарі `FIRE_ROOMS` у секції `ENTITIES`. Фільтр читає пари DXF code/value,
тому нульові координати не сприймаються як межі сутностей. Геометрія, header,
таблиці шарів і будь-які інші TEXT/MTEXT зберігаються. Оригінальний fixture
і `DEMO_DXF` не редагуються; довільні завантажені DXF не трансформуються.

У демо всі три перемикачі початково ввімкнені. Назви та площі на полотні
походять лише з `Room[]`; другий незалежний набір написів у підкладці відсутній.
«Приміщення» керує полігонами та пов'язаними підписами/списком;
«Сповіщувачі» — лише маркерами; «Підписи» — текстом оверлею.
Налаштування підписів можна змінити й при вимкнених приміщеннях: воно
застосується після їх увімкнення. Перемикачі не викликають нового Load.
Список містить повні назви навіть тоді, коли довгі підписи скорочені або
маленькі приміщення не вміщують підпис при віддаленні.

### Архітектура

- `drawing-overlay.tsx` розташований поверх canvas усередині `.stage`.
  SVG малює напівпрозорі полігони з тонким пунктирним контуром; HTML — підписи,
  кнопки-маркери й tooltip. Камера та DXF renderer залишилися з BIM-59.
- `overlay-geometry.ts` проєктує кожну WCS-точку через `worldToScreen` без
  масштабування mm → m. `Room.area` використовується без перерахунку.
  Перетин внутрішніх горизонтальних відрізків на всій висоті підпису (включно
  з рівнями вершин) утримує весь прямокутник у неопуклому/похилому контурі,
  із відступами від стін і viewport. Перевага надається центру кімнати;
  прив'язка зміщується лише за потреби вмістити текст у доступній області.
  Дані або видимість пристроїв не беруть участі в розміщенні. Шрифт не зменшується до
  нечитабельного розміру; довгі назви скорочуються, надто вузькі/невидимі
  приміщення не мають підпису на полотні. Некоректні контури/позиції пропускаються.
- `subscribeViewportChange` об'єднує події в один `requestAnimationFrame`.
  Cleanup знімає підписку й скасовує кадр. Зміна URL/retry перемонтовує canvas
  та оверлей разом; loading/error не показують залишків попереднього оверлею.
- Видимість кімнат і пристроїв — незалежний локальний стан `DrawingCanvas`.
  Проєкції кімнат і пристроїв обчислюються окремо; перемикачі лише фільтрують
  відображення вже розрахованих елементів, не змінюючи їхніх координат.
  Перемикачі не впливають на effect завантаження DXF; нове креслення починає
  з увімкнених шарів. Глобальний `activeLayer` store не використовується,
  оскільки він не описує дві незалежні видимості.
- Контейнер і полігони мають `pointer-events: none`, лише маркери — `auto`.
  Центр кнопки точно збігається з позицією пристрою. Розміри з токенів:
  glyph 20 px (`iconMd`, 24 px `iconLg` на hover/focus), ціль 40 px;
  zoom їх не змінює. Білий контур і легка тінь підсилюють видимість на DXF.
  Tooltip відкривається hover/focus, закривається Escape та обмежений сценою.
  Поза видимою областю й у вимкненому шарі немає прихованих tab-цілей.
- `device-symbol.tsx` — єдине місце майбутньої заміни символів BIM-107.
  Наразі це коло/трикутник/квадрат/ромб із кольорами `tokens.json`.
  `Room` не отримує вигаданих статусів; null-назва та невідома кімната мають
  нейтральні текстові заміни.
- `demo-drawing.ts` містить окремий `DrawingResult` і текст малого DXF для
  локального Blob. Автоматичний тест звіряє текст із оригінальним fixture,
  усі вершини з парсером dxf-viewer і площі з геометрією.

Контракти, вихідні DXF, адаптер BIM-59, store, дизайн-токени та залежності
не змінювалися. Бекенд не потрібний для демо; реальні `rooms`/`devices`
надалі передає викликач. BIM-107 не блокує роботу тимчасових символів.

### Перевірка 23.10.2026

Автоматичні тести охоплюють проєкцію з ненульовим origin, pan/zoom/resize,
неопуклий контур, порожню/некоректну геометрію, null-поля, кадри/cleanup,
типи символів, стани шарів і вузький виняток auth-proxy.

Причина попередньої помилки: підписи обходили лише видимі маркери, тому
перемикання датчиків змінювало їхні позиції. Англомовні написи залишалися
нативними TEXT у DXF й не підпорядковувалися перемикачам оверлею.

У production Chrome через CDP пройдено 73 перевірки, включно з DOM-полігонами
та маркерами, реальними mouse drag/wheel подіями, DPR 2, Tab/Escape/hover,
усіма 8 комбінаціями трьох перемикачів після fit, zoom, pan і resize.
Порівнюються екранні прямокутники підписів/маркерів і вершини полігонів:
відмінності матричної арифметики менші за 0.000001 px для вершин ігноруються,
для DOM-прямокутників перевіряється точна рівність. Перевірено відсутність повторного fetch DXF і заміни canvas при
навігації, синтетичним `webglcontextlost` і retry, malformed DXF, close/reopen,
трьома основними fixture, українським TEXT/MTEXT і важким DXF 9 506 254 байти
(open/pan/wheel/zoom/resize/fit/reopen). Звичайне відкриття оригінального
fixture зберігає всі англомовні написи; їх видалення застосовано лише до демо.
Uncaught browser exceptions не зафіксовано. Знімки демо й tooltip переглянуто:
контури збігаються зі стінами, після вимкнення всіх шарів залишається тільки геометрія DXF.

Повторюваний сценарій: `apps/web/scripts/check-drawing-overlay.mjs`.
Запустіть production server на порту 3100, окремий Chrome із CDP 9334 і виконайте:

~~~powershell
node apps/web/scripts/check-drawing-overlay.mjs
~~~

Адреси можна перевизначити `BIM_PREVIEW_URL` і `BIM_CDP_URL`. Сценарій працює
через вбудовані Node fetch/WebSocket, без Playwright або додаткових залежностей.
Результати та знімки останньої візуальної перевірки: ігнорований
`tmp/bim60-layer-browser/`; попередні прогони — `tmp/bim60-visual-browser/`
та `tmp/bim60-browser/`.

Ці браузерні перевірки й огляд знімків **не замінюють ручне приймання** у
звичайному вікні браузера. Ще потрібні ручні pan/wheel/resize на реальному GPU,
нативний drag із Провідника, оцінка читабельності на довільних щільних планах,
інші браузери й хостинг. Для важкого DXF у цьому проході підтверджені
open/pan/wheel/zoom/resize/fit/reopen через CDP; ручна оцінка плавності ще не виконана.

## Drag & Drop: реалізація та межі перевірки

Input і drop викликають спільну `openFile(File)`. Приймається один непорожній
файл із розширенням .dxf без урахування регістру. PDF/інший формат,
порожній файл і кілька файлів відхиляються українським повідомленням.
Невалідний вибір не замінює поточний DXF; новий валідний файл замінює його.
Input очищається після вибору, щоб дозволити повторний вибір того самого файла.

Поки сторінка змонтована, window handlers запобігають default-навігації
на file dragover/drop, включно з drop над canvas або поза рамкою.
Лічильник dragenter/dragleave керує підсвічуванням; drop/dragend/blur його
скидають. Cleanup прибирає handlers. Object URL належить ref: заміна,
закриття та unmount відкликають його; швидкі batched заміни не покладаються
на виконання effect для кожного проміжного state.

| Сценарій | Фактичний результат |
| --- | --- |
| Dragenter/dragover файла | Підсвічування й preventDefault підтверджено синтетичними DragEvents у production Chrome |
| Коректний DXF після drop | Автоматично відкрився, canvas готовий |
| Інший DXF поверх поточного canvas | Замінив поточний, попередній object URL відкликано |
| PDF, порожній DXF, кілька файлів | Показано відповідні українські помилки |
| Непорожній некоректний DXF, потім коректний | Помилка парсингу, потім успішне відкриття |
| Альтернативний input | Відкриття файла підтверджено через CDP setFileInputFiles |
| Object URL у перевіреній послідовності замін/помилок/закриттів | Створено 6, відкликано всі 6 |
| Небажана навігація | Drop events скасовані; URL залишився /drawing-preview |
| Uncaught exceptions / console warnings/errors у цьому прогоні | Не зафіксовано |
| Drag безпосередньо з Провідника Windows | Не перевірено; синтетичні DragEvents цього не підтверджують |
| Unmount cleanup, тривалий stress/heap-профіль | Переглянуто код cleanup; окремого браузерного stress/heap-тесту не виконано |

Усього у локальному браузерному сценарії пройшли 18 перевірок.

### Що саме вимірює API

`DxfViewer.Load` виконує Clear → DxfWorker.Load → batches/objects →
FitView/controls/Render. Без workerFactory клас DxfWorker працює на main thread.
DxfFetcher накопичує декодований рядок, надсилає parse і викликає parseSync.
DxfWorker надсилає prepare та виконує DxfScene.Build. Font callbacks
надсилають font перед fetch/ArrayBuffer і prepare ПЕРЕД opentype.parse.

Тому performance.now() інтервали такі: початок Load → parse (читання з
початковим overhead); parse → перший prepare (парсинг); кожний font →
prepare (очікування bytes шрифту); решта prepare → повернення Load
(побудова сцени, opentype, Three.js, перший render). Повторні prepare
накопичуються, а не стирають попередній час. При помилці інтервали часткові.
GPU працює асинхронно: окремий час GPU або фактичного показу кадру
не виміряний. Dynamic import canvas не входить у loadMs.

Результати доступні під viewer у «Діагностика завантаження» та Console
за [DrawingViewer load]. Порівнюйте production, холодний/повторні запуски,
стан кешу й обладнання; не змішуйте loadMs із dev compilation.

Власний діагностичний logger використовує явний список дозволених полів:
тільки скінченні числові timings/лічильники та outcome ready/error/cancelled.
URL, імена файлів, access token, сирі Error/Response і довільні додаткові
поля не передаються в console. Ідентифікатор операції наразі не потрібний;
URL не використовується для ідентифікації. Перевірено також DrawingViewer,
адаптер і preview: інших власних діагностичних console-викликів немає.
Це межа логування застосунку; браузерний Network і внутрішні повідомлення
сторонньої бібліотеки не є власними журналами та цим logger не перехоплюються.

### Функції, геометрія та повторні обчислення

Конкретний шлях у встановленій 1.0.50:
DxfScene.Build → _ProcessDxfEntity → _DecomposeDxfEntity →

### Відкладені оптимізації

**Worker і зміни SPLINE не реалізовані; рішення про їх впровадження відкладено.**

Бібліотека підтримує workerFactory і DxfViewer.SetupWorker. Worker може
винести Fetch/parse/Build із UI thread, передавши buffers як transferable;
Three.js objects/Render залишаться на main thread. Це може покращити
чутливість UI, але не зменшує кількості sample і не гарантує скорочення
загального Load. Потрібні перевірки Next.js dev/prod bundling, URL шрифту,
CSP за наявності, termination/error/cleanup та швидкої заміни файла.

Оптимізацію evaluation, reuse scratch/weights/domain, monotonic span,
кеш сцени та повторне використання renderer можна розглядати лише за потреби
і погодженням. Навіть збереження sampling вимагає перевірки координат,
bounds, repeated knots, endpoints і floating-point відмінностей.
Зменшення subdivision/адаптивну апроксимацію не застосовано через ризик
для точності. Перед змінами корисний browser Performance trace;
це рекомендація, а не вже виконана перевірка.

## BIM-63 — інтеграція BIM-47/BIM-62 (29.10.2026)

Маршрут `/drawings/[id]` зберігає повний `DrawingDetail` BIM-63 та отримує ID
після upload BIM-62. Наявний `(protected)/layout.tsx` забезпечує Supabase
авторизацію й AppShell. DrawingViewer, DrawingOverlay, камера та координати
BIM-59/60 не змінювалися. Посилання «Завантажити інше креслення» повертає на `/upload`.

### Фактичний API

Спільний `lib/api.ts` надає `apiFetch`, Supabase access token, `ApiHttpError`
і шлях `DRAWINGS_API_PATH`. BIM-62 та BIM-63 використовують `/api/v1/drawings`.
`NEXT_PUBLIC_API_URL` рекомендовано задавати як origin API; клієнт також
не подвоює `/api/v1`, якщо цей префікс уже присутній у базовій адресі.

`GET /api/v1/drawings/{id}` реально існує й повертає плоску Pydantic-модель
у snake_case: `owner_id`, `original_file_name`, `storage_path`, `created_at`,
`source_download_url`, `source_download_url_expires_at`, а також `id`, `units`,
`status`. `normalizeDrawingDetail` перевіряє ID/поля і переводить назви в camelCase.
Дати FastAPI передає як рядки. Статус помилки деталей — `failed`, не `error`.

FastAPI зберігає `units: "from_file"` до визначення одиниць. Клієнт зберігає
це значення й показує «очікується визначення з файла», не підміняючи його `mm`.
Спільний `DrawingDetailResponse` поки звужує units до `mm | m`; локальний тип
`DrawingDetail = Omit<DrawingDetailResponse, "units"> & { units: RequestedDrawingUnits }`
описує цю відмінність без зміни схем чи generated-файлів.

`POST /api/v1/drawings/{id}/process` повертає HTTP 200 із
`{ drawing_id, status: "accepted", message }`. Це `ProcessingAccepted`,
а не `ProcessingJob`: заглушка не створює job, не змінює статус креслення
й не запускає повний пайплайн. UI показує: «Запит прийнято сервером, але повна
обробка ще недоступна. Обробку не запущено, результат не створено».
Клієнт один раз оновлює деталі після POST; автоматичного polling немає.
Повторне натискання під час запиту блокується, включно з подвійним click.

Реальний адаптер навмисно не має `getJob`: `/processing-jobs/{id}` відсутній.
Опитування кожні 2 секунди з лімітом 2 хвилини збережене тільки для адаптера
з підтримкою jobs — зараз це явний локальний деморежим. Статус `processing`
у реальному GET сам по собі не вмикає polling. «Оновити стан» працює вручну.
Запити перериваються, а таймери очищуються при зміні ID/демонтуванні.

### Оригінал і результат

Оригінал відкривається за `sourceDownloadUrl`, навіть без обробки. Кеш містить
ID і режим API/demo; стан сторінки скидається при зміні ID. Уже завантажений
DXF не перезавантажується через ротацію signed URL чи перемикання шарів.
«Оновити файл» отримує свіжі деталі й явно оновлює перегляд.

«Завантажити оригінальний DXF» завжди спочатку робить GET, перевіряє URL і expiry,
а потім читає файл без bearer token API. Blob URL звільняється після передачі
браузеру. Відсутній URL, прострочення, HTTP-помилки та порожній файл обробляються
окремо. Signed URL не записуються в localStorage і не логуються клієнтом.

GET наразі не повертає Room[]/Device[] або URL обробленого DXF.
Кнопка «Завантажити DXF результату» вимкнена, доки немає готового результату
з власним downloadUrl; поруч є пояснення. `sourceDownloadUrl` не використовується
замість нього. Фронтенд не створює згенерований DXF.
Навіть GET зі статусом processed без результату не створює фіктивних масивів.

BIM-54 має окремий `/api/v1/cad/extract-rooms`; він ще не підключений до `/process`.
Автоматичний розрахунок, jobs, отримання результату й згенерованого DXF залишаються
залежними від бекенду. Бекенд Дарії в цій інтеграції не редагувався.

### Деморежим

Задати `NEXT_PUBLIC_DRAWING_DEMO=true`, запустити development-сервер і відкрити
`/drawing-preview?result=true`. Кнопка «Відкрити демо результату» використовує
локальний DXF та Room[]/Device[] BIM-60, без мережевого API. Перемикання ID
перевіряє порожні результати, кімнати без пристроїв, failed, відсутні й прострочені
посилання та HTTP/мережеві помилки. Згенерованого DXF у демо немає: downloadUrl=null.

Production ігнорує прапорець. `/drawings/[id]` завжди захищений; production
`/drawing-preview` також вимагає сесію. Моки не підміняють production-відповіді.
