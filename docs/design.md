# Design System — Fire Safety BIM MVP

**Призначення:** вебплатформа для завантаження архітектурного креслення, перегляду плану та роботи з даними системи пожежної сигналізації й оповіщення.

> Цей документ визначає UI-конвенції продукту. Кольори та позначення для креслень є дизайнерськими рішеннями інтерфейсу, а не заміною нормативних вимог до пожежного проєктування. Перед використанням у виробничому процесі значення та позначення потрібно узгодити з командою й перевірити щодо застосовних стандартів.

## 1. Принципи дизайну

- **Інженерна ясність:** інтерфейс має бути точним, спокійним і передбачуваним.
- **Пріоритет креслення:** план займає основну робочу область; панелі інструментів не повинні перекривати важливі частини плану без потреби.
- **Колір має значення:** кольори шарів та статусів використовуються послідовно й не змінюють значення між екранами.
- **Пояснювані стани:** завантаження, помилки, відсутність даних і завершення операцій мають бути видимими.
- **Безпечні дії:** деструктивні або незворотні дії повинні мати чіткий текст і підтвердження, якщо це потрібно.
- **Доступність:** не передавати важливу інформацію лише кольором; доповнювати її текстом, іконкою або типом лінії.

## 3. Типографіка

**Основний шрифт:** Inter. Якщо Inter недоступний, використовувати системний sans-serif.

| Стиль | Розмір / line-height | Вага | Використання |
|---|---|---|---|
| `display` | 32 / 40 px | 600 | Великі заголовки, лише за потреби |
| `heading.h1` | 24 / 32 px | 600 | Заголовок сторінки |
| `heading.h2` | 20 / 28 px | 600 | Заголовок секції |
| `heading.h3` | 16 / 24 px | 600 | Заголовок картки або панелі |
| `body.large` | 16 / 24 px | 400 | Основний текст у важливих поясненнях |
| `body` | 14 / 20 px | 400 | Основний UI-текст |
| `body.medium` | 14 / 20 px | 500 | Акцентний текст, значення в таблицях |
| `label` | 12 / 16 px | 500 | Підписи полів і таблиць |
| `caption` | 12 / 16 px | 400 | Підказки, метадані |
| `numeric` | 13 / 20 px | 500 | Числа, координати та технічні значення |

Правила:
- Не використовувати надто дрібний текст для критичних статусів.
- Для числових колонок за можливості використовувати вирівнювання праворуч.
- Назви статусів і важливі повідомлення мають бути читабельними при масштабуванні.
- Довгі назви файлів і значення не повинні ламати компонування: дозволено перенесення або обрізання з доступним повним значенням.

- Велика кнопка: 48 px.

- Основні відступи між секціями: 24 px.
- Відступ усередині картки: 16–24 px.

## 5. Радіуси, межі та тіні

| Токен | Значення | Використання |

| `radius.md` | 8 px | Поля, кнопки, невеликі картки |
| `radius.lg` | 12 px | Основні картки та панелі |
| `radius.xl` | 16 px | Великі модальні вікна, якщо доречно |

Межі:
- Звичайна межа: `#E2E8F0`, 1 px.
- Активна межа: `#2563EB`, 1–2 px.
- Межа помилки: `#B91C1C`, 1 px.

Тіні мають бути стриманими. Не використовувати тіні для кожного елемента; вони потрібні для модальних вікон, випадаючих меню та шарів, які мають візуально відокремлюватися від фону.

## 6. Компоненти

### 6.1 Кнопки

Варіанти:
- **Primary:** головна дія сторінки, наприклад «Завантажити креслення».
- **Secondary:** другорядна дія, наприклад «Скасувати».
- **Tertiary / ghost:** дія без виразного контейнера, наприклад керування панеллю.
- **Danger:** видалення або інша потенційно руйнівна дія.

Стани:
- Default
- Hover
- Pressed
- Focus-visible
- Disabled
- Loading

Правила:
- Текст кнопки має починатися з дієслова й описувати дію.
- Під час завантаження показувати індикатор і не допускати повторного запуску тієї самої операції.
- Не використовувати лише колір для позначення disabled або loading.
- Для деструктивної дії використовувати зрозумілий текст; підтвердження потрібне, якщо дію складно скасувати.

### 6.2 Поля введення та завантаження файлу

Елементи:
- Label
- Input / textarea / select за потреби
- Допоміжний текст
- Повідомлення про помилку
- Стан disabled
- Focus ring

Стани:
- Default
- Hover
- Focus-visible
- Filled
- Error
- Disabled
- Loading, якщо поле бере участь у запиті

Правила:
- Label має залишатися видимим після введення значення.
- Помилка пояснює, що сталося і як це виправити.
- Для завантаження файлу показувати назву, формат, розмір (якщо доступно), прогрес і можливість скасування (якщо підтримується).
- У повідомленнях про формат файлу перелічувати лише формати, які реально підтримує реалізація. Не обіцяти підтримку DWG, якщо вона не підтверджена; для MVP формат потрібно погодити з розробниками.

### 6.3 Таблиця

Структура:
- Заголовок таблиці.
- Рядки даних.
- Необов'язкові сортування та фільтри.
- Стани порожнього результату, завантаження та помилки.
- За потреби — пагінація.

Візуальні правила:
- Заголовок має чітко відрізнятися від рядків даних.
- Розділювачі тонкі й нейтральні.
- Hover виділяє рядок, але не імітує вибір.
- Selected row має окремий, помітний стан.
- Текст у клітинках вирівнюється послідовно; числа можуть бути вирівняні праворуч.
- Довгі значення не повинні перекривати сусідні стовпці.

Стани таблиці:
- Loading
- Default
- Hover row
- Selected row
- Empty
- Error
- Disabled, якщо таблиця недоступна

### 6.4 Бейдж статусу

Використовувати для коротких статусів об'єкта, обробки або перевірки. Бейдж повинен містити текст, а не лише кольорову крапку.

Рекомендовані статуси для UI:
- `У черзі` — нейтральний.
- `В обробці` — інформаційний.
- `Успішно` — success.
- `Потребує уваги` — warning.
- `Помилка` — danger.
- `Вимкнено` — disabled / neutral.

Це приклади статусів інтерфейсу, а не нормативна класифікація пожежних порушень.

### 6.5 Панель плану (Plan Panel)

Призначення: перегляд архітектурного плану та керування видимістю шарів і об'єктів.

Основні частини:
- Полотно плану.
- Панель інструментів: масштабування, переміщення та інші дії, якщо вони реалізовані.
- Список шарів із перемикачами видимості.
- Легенда позначень.
- Вибраний об'єкт і його деталі, якщо доступні.
- Індикатор завантаження або повідомлення про помилку.

Стани:
- Empty: план ще не завантажено; показати коротку інструкцію та дію завантаження.
- Loading: показати прогрес або індикатор обробки.
- Ready: план відображається, доступні інструменти, які підтримує MVP.
- Selected: вибраний об'єкт має контрастну обводку.
- Layer hidden: об'єкти шару не відображаються, стан перемикача очевидний.
- Error: пояснення помилки та доступний наступний крок.
- Unsupported file: показати підтримувані формати, підтверджені реалізацією.

Рекомендації:
- Підтримувати нейтральний фон полотна, щоб об'єкти креслення були помітні.
- Не змінювати семантику кольорів шарів між екранами.
- Показувати назву шару й легенду.
- Важливі об'єкти відрізняти не лише кольором, а й формою/обводкою/підписом.
- Не вигадувати автоматичне виправлення або BIM-функції, яких немає в MVP.

## 7. Загальні стани та зворотний зв'язок

Для інтерактивних компонентів передбачити, де це доречно:
- **Default:** звичайний стан.
- **Hover:** елемент реагує на наведення.
- **Pressed:** дія активована.
- **Focus-visible:** видима клавіатурна рамка.
- **Disabled:** дія недоступна; причина має бути зрозумілою, якщо це не очевидно.
- **Loading:** операція триває, повторний запуск контролюється.
- **Success:** операцію завершено.
- **Warning:** є проблема, що не обов'язково блокує роботу.
- **Error:** операцію не виконано; повідомлення має пояснювати наступний крок.
- **Empty:** немає даних; запропонувати доречну дію.

Повідомлення повинні бути короткими, конкретними й написаними зрозумілою мовою. Не показувати користувачу необроблені технічні stack traces.

## 8. Доступність і адаптивність

- Підтримувати клавіатурну навігацію та видимий `focus-visible`.
- Не передавати значення тільки кольором: використовувати текст, форму, піктограму або тип лінії.
- Перевірити контраст тексту й елементів керування на реальних компонентах; ціль — WCAG 2.2 AA там, де застосовно.
- Не покладатися на колір як єдиний спосіб позначення порушення.
- На вузьких екранах робочі панелі можуть перебудовуватися, але пріоритетні дії та стан операції мають залишатися доступними.
- Збільшення масштабу креслення не повинно автоматично збільшувати текст навігації, якщо це не передбачено реалізацією.

## 9. Правила використання токенів

- Значення з `tokens.json` є єдиним джерелом правди для названих кольорів, розмірів, радіусів і тіней.
- У коді не дублювати довільні значення, якщо для них уже існує токен.
- Якщо значення змінюється, оновлювати токен і цей документ разом.
- Якщо потрібен новий токен, додавати його з узгодженою назвою та описом.
- Токени для креслення використовувати послідовно в легенді, на плані та в панелях керування.

## 11. Межі документа

Ця дизайн-система описує візуальні правила UI для MVP. Вона не визначає інженерні розрахунки, нормативні вимоги, правила розміщення сповіщувачів або офіційні позначення пожежної сигналізації. Такі рішення мають бути перевірені профільними фахівцями й відповідними стандартами.
