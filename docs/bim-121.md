## Фактичні API

Префікс — `/api/v1`, авторизація — через наявний `apiFetch`.

| Запит | Відповідь та поведінка клієнта |
| --- | --- |
| `POST /drawings/{id}/process` | `{drawing_id, status: "processing"}`; після завершення — GET |
| `POST /drawings/{id}/place` | `{drawing_id, status: "processed", result_path}`; після завершення — GET; `result_path` не використовується як URL |
| `GET /drawings/{id}` до обробки | Плоска snake_case відповідь нормалізується в існуючий detail |
| GET після process/place або за помилки | DrawingResult із rooms/devices та незалежними тимчасовими посиланнями |

Клієнт також приймає DrawingResult безпосередньо з POST. `accepted` більше
не підтримується. Реальний API не опитується за таймером; старий обмежений
job polling лишився тільки для явного demo-адаптера. Відкриття сторінки
ніколи не запускає process. Повторна обробка потребує підтвердження, оскільки
сервер перезаписує приміщення. Спільне блокування захищає від подвійних кліків
та одночасних process/place; POST автоматично не повторюються.

`Room.polygon` і `Device.position` передаються в наявний оверлей без зміни
координат WCS. Перетворення в екранні координати виконує лише viewer.
Координати — у DXF одиницях mm/m; `Room.area` вже в м², `height` — у метрах.
Масиви замінюються новими даними, а не доповнюються при кожному GET.

## Чому потрібна вузька зміна API

Без неї після process було неможливо отримати кімнати до place. GET тепер
повертає DrawingResult також для processing/error/failed; failed нормалізується
до контрактного error. Неактуальні прилади та старий результат не видаються,
поки креслення не processed. Бізнес-логіка пошуку, правил і розміщення не змінена.

У спільну схему DrawingResult додано необов'язкові `sourceDownloadUrl` та
`sourceDownloadUrlExpiresAt`. Обидві моделі перегенеровано; Python-генерація
також підхопила вже наявний у схемі контракт Rule, без зміни алгоритмів.
Source використовується для підкладки, `downloadUrl` — лише для згенерованого DXF.
Оновлення результатів не перезавантажує canvas і не скидає камеру.
Перед кожним завантаженням клієнт отримує свіжий GET, перевіряє строк дії URL
і завантажує файл без API Authorization. Відсутнє/некоректне посилання має
зрозуміле повідомлення; URL не зберігається як постійне значення.

Frontend та API слід розгортати узгоджено: старий GET не має source URL
для processed і не повертає кімнати після process.

## Відомі обмеження сервера

- Чинні process/place записують status=error, але не записують error_message;
  міграції цієї бази також не містять цієї колонки. Цю прогалину BIM-119 не
  приховано: клієнт показує безпечну помилку запиту, а після повторного відкриття —
  загальне повідомлення. Якщо errorMessage надійшов, відомі публічні повідомлення
  відображаються/перекладаються, довільні діагностичні дані не показуються.
- Поточний place не перевіряє підтвердження кімнат, використовує перше правило
  з legacy threshold. Ця логіка не змінена в BIM-121 і потребує узгодження
  з BIM-72/BIM-71 та власником серверного розміщення.
- Для `from_file` чинний process не зберігає resolved_units. UI не вигадує їх
  і не масштабує геометрію повторно; площу розраховує існуючий DXF parser.
- Старий коментар ProcessingJob у схемі описує асинхронний варіант; у чинному
  production router endpoint processing-jobs відсутній.

## Перевірки

Залежності frontend встановлені `npm ci --no-audit --no-fund`; lockfile не змінено.
Node 24.12.0 видає engine warning для jsdom (потрібен щонайменше 24.15.0
у гілці Node 24), проте виконані тести проходять. API перевірено на ізольованому
Python 3.12 у `apps/api/.venv`, без зміни системного Python.

| Команда | Що перевіряє |
| --- | --- |
| `npm run contracts:generate` | TypeScript відповідає схемі |
| `npm run typecheck` | Web і contracts |
| `npm run lint` | ESLint |
| `npm run test` | API-адаптер, UI, повний клієнтський цикл із fixtures, регресія viewer і contracts |
| `npm run build` | Production build Next.js |
| `ruff check apps/api` | Python lint |
| `mypy apps/api/src --config-file apps/api/pyproject.toml` | Типи API |
| `python -m unittest discover -s apps/api/tests` | 51 тест, включно з реальним DXF parser/writer та замоканими Supabase/Storage |
| `node apps/web/scripts/check-drawing-overlay.mjs` | Chrome/WebGL: pan/zoom/fit, DPR, шари, tooltip, кирилиця, повторне відкриття, помилки |

На Windows використовується `npm.cmd`; Python-команди — з локального virtualenv.
API unit tests використовують лише наявні тестові значення
`SUPABASE_URL=https://mock.supabase.co`, `SUPABASE_SERVICE_ROLE_KEY=mock-key`.
Браузерний сценарій запускається проти локального `npm run dev` на :3100
та окремого headless Chrome CDP :9334; знімки й результати — в ігнорованому tmp.

Результат фінального локального запуску: TypeScript, ESLint, production build,
Ruff і Mypy успішні; **193 web + 8 contract + 51 API тестів пройдено**.
У Chrome пройдено **75 перевірок** переглядача, необроблених винятків немає.

Дві наявні API-перевірки виправлено для Windows: порівняння `Path` замість
Unix-префікса рядка та універсальні переноси рядків під час читання DXF із bytes.
Перевірка шару не послаблена; додатково звіряються кількість і координати INSERT
з Device[] після повного process → GET rooms → place → GET результату.

**Це не перевірка розгорнутого API.** React-тести використовують fixtures,
API-тести — реальні parser/writer із mock Storage/DB, браузер — локальний preview.
Без налаштованого тестового API та чинної сесії не перевірено наскрізний
авторизований сценарій на хостингу, підписи Supabase та фактичне збереження даних.

## Перевірка перед merge

1. Розгорнути API та web цієї гілки у тестовому середовищі з чинними налаштуваннями.
2. Завантажити дозволений тестовий `01_simple_rooms_mm.dxf`.
3. Відкрити креслення: лише GET, оригінальний план; натиснути «Обробити».
4. Перевірити кімнати й площі до розміщення, їх збіг із контурами плану.
5. Натиснути «Розмістити»; перевірити прилади, tooltip, шари, pan/zoom/fit.
6. Оновити стан і відкрити креслення повторно: без POST та дублювання геометрії.
7. Завантажити DXF результату, перевірити в ньому прилади; повторити після
   закінчення строку дії попереднього URL.
8. Перевірити порожні rooms/devices, відсутній файл, HTTP 400/422/500 і помилку
   обробки. Повторний process виконувати лише після явного підтвердження.
