## Implemented behavior

**BIM-78:** findings list and plan highlighting; bidirectional selection; pan to real device coordinates or an interior point of the referenced room, preserving zoom. Multiple findings at the same location remain separately selectable. Missing spatial data stays accessible in the panel. Selection clears when a finding disappears. Rules open by database ID, with independent review/verified/unknown states. Conflicts display both supplied sources, clauses and values with “Потрібне рішення інженера”.

**BIM-218:** Ukrainian critical, warning, insufficient-data and conflict states; filtering; selected-row scrolling; loading, unchecked, successful empty and retryable error states. A 396px desktop panel uses the existing Inter font, shared buttons, rule badges, palette and original critical symbol. At narrower widths the panel stacks below the plan. Editing controls stay in the Plan tab so a findings view cannot hide an active editor's fields.

**BIM-219:** generated `Finding` type; `GET /api/v1/drawings/{drawing_id}/findings` through existing authenticated `apiFetch`; abort signals and response validation; 401/403/network/server errors remain errors. Findings queries are keyed by drawing and drawing-detail revision. Successful placement and existing room/device/zone/exit mutations refresh the drawing and thereby obtain a new findings snapshot. Old requests cannot overwrite a new revision. Results are hidden during refresh/uncertain writes, with no added polling, frontend regulatory calculations or production mocks.

The existing source URL remains stable across results refreshes. The viewer is retained between Plan and Findings tabs; findings refresh does not invoke fit, pan or DXF reload. Viewport subscriptions are installed before ready controls paint, preventing an initial zoom event from racing the subscription. A separate layer toggle controls findings without changing room/device layers. Existing BIM-182 zone/exit editing, draft guards and BIM-122 provenance remain in place and covered by the regression suite.

## Deployment blockers and contract limitations

On 27 November, `https://intelligent-bim-api.vercel.app/openapi.json` did not advertise the findings route or Finding schema. A GET to `/api/v1/drawings/00000000-0000-0000-0000-000000000001/findings` returned **404**. The repository router exists in the baseline, so this is deployment evidence, not a successful authenticated integration check. No credentials were supplied for this execution; no real account/drawing was modified.

The actual backend `conflictDetails` contains `deviceType`, `valueKind`, `appliedRuleId`, and `rules[]` with database `id`, textual `ruleId`, `document`, `clause`, `value`, `maxProtectedAreaM2`, `verificationStatus`. UI mapping uses database IDs. Units are displayed only for recognized backend value kinds.

The catalog endpoint supplies a formatted `value` string but no separate unit field. The card preserves that value and truthfully indicates an unavailable separate unit. No unit or normative clause is inferred from a rule name.

Backend `_detect_rule_conflicts` already reports a stricter applied value in its message and `appliedRuleId`. This conflicts with the handoff's engineer-decision intent. The frontend preserves the supplied message, shows both requirements and the decision-required label, and makes no precedence decision. This backend/product discrepancy remains for the responsible owners; regulatory logic was not changed.
